# Artiflow

International marketplace for digital artists: portfolios, original characters (OCs), adoptables and commissions. Product language is English; prices in USD.

## Source of truth

The product/brand direction lives in `docs/brand/Aqua_Product_Brand_Blueprint.docx`. Treat it as the briefing. When something is ambiguous, read the blueprint before guessing — it marks what is a decision vs. a hypothesis.

The executable plan lives in `docs/roadmap.md` (phases, item status, feature briefs, stakeholder requests log). Claude owns it: log every stakeholder request there, update statuses when work lands, and check it before starting a feature.

Key decisions already made (per blueprint):

- Positioning: global marketplace, English-first, USD-first.
- Business model: 10% platform fee on transactions; paid plans (do not remove the fee): **Flow+** (US$6.99/mo) for fully custom profiles (code still calls it `pro`) and a higher tier (US$9.99/mo, name TBD — working name "Flow+ Live") adding live streaming. Prices and perks live in `src/lib/plans.ts`; `/plans` shows them (no checkout yet).
- Visual direction: **Aqua** (light, modern, art-first). Name "Artiflow" is a working candidate — not final.

Still undecided: final brand name & domain, legal entity, payments provider, moderation policy, premium customization scope.

## Themes: Aqua (light) & Ember (dark)

Two themes of one design system, not two brands ("Artiflow Aqua" / "Artiflow Ember"). Components use only semantic tokens (`bg-surface`, `bg-canvas`, `text-ink`, `text-on-ink`, `bg-scrim`, `text-lilac-ink`, `text-star`, `text-like`, `text-danger`…) — never `bg-white` for surfaces or raw hex. Raw values live per theme in `globals.css` under `:root, [data-theme="aqua"]` and `[data-theme="ember"]`; any element can re-scope with `data-theme` (the picker previews do).

Ember maps the same roles to its own palette: ocean → Ember Red `#FF3948`, sky → Flame Orange `#FF762E`, mint → Blaze Pink `#F04488`, lilac → Ember Violet `#9857F5`, muted → Ash `#A8B0C2`, canvas → Night `#0B101C`, surface → Charcoal `#171C2B`, ink → Cloud `#F4F5FA`; display font → Space Grotesk. Profile accents point at these tokens, so they follow the theme.

Physical "paper" objects (stickers, hang tags, paint chips, polaroids, seals) use `bg-paper` / `text-on-paper` / `text-paper-muted`, which stay light in both themes — like real paper on a dark table. The `grain` utility adds paper texture behind a surface (never over artwork).

The choice (`aqua` | `ember` | `system`, default `aqua`) is stored in localStorage and applied by an inline script before paint (`src/lib/theme.ts`) — no cookie, so pages stay static/PPR. Picker: `src/components/site/theme-menu.tsx` in the header. `dark:` variant = Ember.
Radii: input `10px`, button `12px`, card `16px`, panel `24px`.
Spacing scale: 4, 8, 12, 16, 24, 32, 48, 64 px.

- Next.js 16 (App Router, TS, Tailwind v4, Turbopack, `src/` dir).

## Conventions

- Everything in the repo is English: code, comments, UI copy, docs.
- Cache Components + Partial Prefetching are on. Await `params` / read cookies **inside** `<Suspense>`; cache data with `"use cache"` + `cacheLife` + `cacheTag`, and invalidate with `updateTag` in Server Actions.
- Keep client components small leaf islands (buttons, composer); everything else is a Server Component.

Replace demo art with uploads from consenting artists before launch. Pushes to `main` deploy production from Git (the build fetches the demo art); `vercel build --prod && vercel deploy --prebuilt --prod` from a clean checkout also works.

## Profile customization (`/customize`, `/[handle]/about`, `/shop`)

- One JSON document per profile, `profiles.customization` (theme preset or own colors, background pattern/image, name font/color/gradient/effect, button shape/style, sidebar side, equipped frame, custom CSS), plus `profiles.about` (the About board). Schemas, presets and the free/Flow+ split: `src/lib/customization/model.ts` + `about.ts`. Rendering: `style.ts` turns it into CSS variables on the profile **canvas** (`[data-profile-canvas]` in `[handle]/layout.tsx`), so existing `bg-surface`/`text-ink`/`bg-accent` components pick up the artist's palette.
- Gating: `gateCustomization()` drops Flow+ fields at render time (kept in the DB, so a lapsed plan degrades and comes back). Editor previews everything ("try before you buy"); `saveCustomization` (`src/app/(site)/customize/actions.ts`) refuses paid fields for free accounts. No column grants on these columns: that action is the only writer (secret key, after session + plan + ownership checks).
- Custom CSS (Flow+): validated in `css.ts` (no @import/@font-face, escapes, markup or scriptable values; `url()` only our art storage or data: images), wrapped in `@scope` at render; the canvas has `contain: paint` + `isolation` so it can't cover site chrome. HTML blocks render in an empty-sandbox iframe with a CSP (no scripts, no outside images).
- CSS hooks: profile parts carry stable `data-part` attributes (name, handle, headline, bio, draws, avatar, banner, stats, actions, meta, card, post, board, block) — the public API for custom CSS and the CSS helper's recipes (`src/components/customize/css-panel.tsx`). Keep them when restructuring the profile; add new ones rather than renaming.
- Edit profile (`edit-profile-dialog.tsx`): name, headline, bio, pronouns, location, links, what you draw (`profiles.headline/pronouns/location/links/draws`, written as the user under RLS via `updateProfileDetails`). Platforms are detected from the URL (`src/lib/profile/links.ts`).
- What you draw: `profiles.draws` (enum `draw_tag`). Subjects (Humans, Anthro / furry, Humanoids, Ferals, Ponies) are asked at sign-up (metadata → `handle_new_user`, or `claimHandle` for social sign-ups); specialties (OC design, backgrounds…) are added in Edit profile. List and labels: `src/lib/profile/draws.ts`; picker: `src/components/profile/draws-picker.tsx`. The profile shows labels ("Furry artist", "Draws it all") linking to `/explore/studios?draws=…#studios`, where `studio-board.tsx` filters the open studios (URL is the state).
- About board: free-form blocks (text, list, image, sticker, html) in 1000 board units, scaled with container units; stacks in reading order under 640px. Editor: `src/components/customize/board-editor.tsx` (drag/resize/rotate, snap, undo). Images go on at their real size on a desktop profile (`realSize()` in `about.ts`: 1000 units = 796px), with no frame, and are never cropped (`object-contain`); they're served as uploaded (no re-encode, see "Images"), so pixel art stays sharp.
- Frames: catalog + placeholder prices in `src/lib/frames.ts`, SVG art in `src/components/frames/avatar-frame.tsx`, ownership in `public.owned_frames` (server writes only). Free frames are claimed from `/shop`; paid ones wait on checkout.
- Demo: `@pebblecat` in mock-db is a fully decorated Flow+ profile + About board.

## Explore (`/explore`): the salon wall

Concept: a **salon hang**, floor to ceiling and edge to edge: everything on Artiflow (gallery pieces, posts, characters, adoptables, commission examples), as many pieces as fit, each at its own shape. Unlike the home feed, which follows a piece through its stages, Explore is for looking at art. Asked for by Robin and Amanda (2026-10-12) and the project lead (2026-10-14). Deliberately not a Pinterest grid: art is never cropped or enlarged past its pixels, so a 64px pixel icon hangs small on its mat.

- Page: `src/app/(site)/explore/page.tsx`. Static masthead ("Everything, wall to wall."); the search box and the wall read the URL and stream in. Controls (`src/components/wall/rail.tsx`, sticky under the header): tabs Everything / Art / Characters / Adoptables with counts, "Open for commissions", palette as paint dabs (the `MOODS`), order Mix / Trending / Newest / Shuffle (seeded, `?seed=`), active-filter chips, tile size. Every control is a link and the URL is the state (`?q=&show=&color=&open=1&sort=`); search is a `next/form` GET form. The header's Explore menu leads here first ("Explore the wall"); the feed's mood names link to `/explore?color=…`.
- Tiles (`tile.tsx`): justified rows (`salon-rows` utility in `globals.css`: `--row` per screen and per tile size), the tile takes the art's shape kept between 1:2 and 12:5 (`mat.ts`), the art sits whole on a mat tinted with its main color (`ListingArt`). Small paper markers: hang tag (adoptable price, "Adopted ♥"), ticket ("from $55"), folder tab (character name + colors), pencil "WIP"/"sketch"; GIF and set-count badges; hover shows title, artist and the heart. Tile size S/M/L is per browser (localStorage, `data-wall-size` on `<html>`, set before paint by `tileSizeScript`).
- GIFs (`gif-play.ts`): the still frame (`ImageAsset.still`, the GIF's thumb, set by `toImageAsset`) until the tile is half on screen; then the first 6 on screen play (one shared IntersectionObserver); none autoplay with reduced motion (hover/focus plays). GIFs without a thumb play as they load.
- Viewer (`viewer.tsx`): a dialog with the art as big as fits (never past its pixels), the set's pictures, and a paper wall label (kind, date, artist, price / "Taking commissions from", palette chips + mood links, likes, the main action to its own page, Save). ← → walk the wall; nearing the end loads the next page; closing focuses the tile you ended on. "More by" the artist from what's loaded.
- Paging (`salon.tsx`): the server renders 60 tiles; `loadWallPage(query, offset)` (`explore/actions.ts`) re-runs the same filter for the next 60 as the end comes within 1200px. No duplicates (ids).
- Data: `src/lib/wall/` — `query.ts` (pure, tested in `query.test.ts`: `WallItem`, `parseWall` / `wallHref`, `runWall` filters + search (`relevance` from search) + sorts, `spreadArtists` so one artist doesn't fill a row, `wallCounts`), `catalog.ts` (cached `getWallCatalog()`, tags `explore-wall` (`WALL_TAG`, gallery actions invalidate it) + `explore`, `feed`, `listings`): real pieces, characters, adoptables, open/waitlist services' examples (Supabase) + demo artists + the pool (`getExploreData().wall`, same ids so saves still work) + feed posts with pictures. **One tile per artwork**: adoptable > character > gallery piece > commission example > post. The heart saves art / post / character / demo service; real adoptables and services have none (not favoritable kinds). Move paging into Postgres past a few thousand pieces.
- Tests: `tests/e2e/explore.spec.ts`.

## Home feed (`/`)

Concept: an exhibition where **the art sets the light** — deliberately not a social timeline (no X/Instagram three-column layout, avatar gutters or sidebars of widgets).

- Page: `src/app/(site)/page.tsx` — static masthead ("Fresh off the easel."), then the viewer-dependent feed streams in `<Suspense>`. Filters are URL params: `?feed=following` and `?stage=finished|wip|sketch|update`.
- Room light: a fixed `#feed-light` layer (`ambient-light` utility in `globals.css`) re-lights the artwork's most vivid swatches (`glowOf()` in `palette.ts`) as a pale wash (Aqua) or low glow (Ember) via registered `@property` colors; `feed-light.tsx` swaps them as posts cross the middle of the screen and renders the palette rail (color minimap, xl+). Hue comes from the art, lightness from the theme, so contrast never depends on the art.
- Pieces (`art-post.tsx`): plate + museum-style wall label, alternating sides on desktop; label splits around the art on phones. Plates (`art-plate.tsx`) are justified rows that never crop, framed by stage: finished → floating with `art-glow`, WIP → crop marks, sketch → spiral sketchbook. Labels show a sketch → WIP → finished track, copyable palette chips + mood, reactions (like splashes the art's colors; likes, comments and reposts are real) and the newest comment as a handwritten margin note.
- Posting (`canvas-composer.tsx`; visitors get the same `canvas-card.tsx` as a sign-in invitation): a composer-looking "blank canvas" under the filters (stage chips preselect the post type), plus a floating **Post** button once it scrolls away, opening the same composer in a dialog. After posting, the dialog closes and the page scrolls back to the top of the feed. Up to four images per post.
- Comments and reposts (`src/components/social/`): one `<CommentsPanel>` and one `<RepostDialog>` per page (home and profile), opened from any button through window events (`events.ts`, `targets.ts`). Reposting a repost pins its original. Reads and writes go through `src/app/(site)/comment-actions.ts` and `repostPost` in `[handle]/actions.ts`; counts, the newest comment and reposted originals come from `hydratePosts` (queries.ts) + `conversation.ts`.
- Loading: placeholders mirror the real layout (the feed's fallback renders the real filters and canvas card) and use the `skeleton` utility, which stays invisible for ~350ms, then breathes slowly. The room light stays dark until the first artwork lights it (`data-lit`).
- Text-only posts are signed studio notes (`studio-note.tsx`) with a commission ticket, adoptable hang tag or pinned polaroid (`note-embeds.tsx`). Discovery comes as interludes between pieces (`interludes.tsx`): open studios, a studio visit, a tag marquee.

## Sign in & join (`/sign-in`, `/join`)

Concept: the artist's desk, seen from above. Deliberately not a split-screen SaaS login.

- Layout: `src/app/(auth)/layout.tsx` (persists across both routes, so switching tabs swaps only the sheet and the art). It's a self-healing cutting mat (`mat-grid`, `ruler-x/y` utilities; rulers track the pointer, `ruler-cursor.tsx`) lit by a fixed `#desk-light` `ambient-light` layer (`light.ts`, `lightDesk()`).
- Art side (`desk-art.tsx`, desktop): sign-in shows a stack of community prints signed in pencil (edition · title · artist). Every 6.5s the top print is pulled off and slipped under the rest, and the desk takes its colors (`print-stack.tsx`, pausable). Join shows *your* blank canvas with construction lines that draw themselves in. It signs itself with the handle you type, pins your inviter's polaroid and note, and gets stamped when the account is made (`blank-canvas.tsx`, shared state in `desk.ts`). Phones get a small fan of prints tucked behind the sheet.
- Sheet (`auth-sheet.tsx`): a binder page with index tabs (Sign in / Create account). Forms are client islands (`sign-in-form.tsx` with an in-place password reset, `sign-up-form.tsx`). Handle check is debounced against the server, with suggestions when taken (`handle-field.tsx`). Password strength is a paint stroke named after drawing stages, rough sketch → fully rendered (`lib/auth/password.ts`). The invite code is a sealed envelope (`invite-envelope.tsx`). `/join?invite=CODE` opens it already checked.
- Server Actions: `src/app/(auth)/actions.ts` (mock: nothing is stored). Rules shared with the client live in `src/lib/auth/` (handles, password, invites). Desk props (pen-tablet stylus, wax seal, construction sketch) are SVG in theme tokens: `desk-props.tsx`.

## Plans (`/plans`)

Concept: every artist gets an **artist trading card**; a plan is the card's finish. Free = matte card stock, Flow+ = foil, Flow+ Live = live holo (rainbow + glitter, LIVE badge, rising hearts). Deliberately not a SaaS pricing table.

- Page: `src/app/(site)/plans/page.tsx`. Hero ("Pick your finish."), then the viewer's own card (streams in, signed-in only), then the three catalog cards fanned on the table, then the fee as a hang tag. Static except the viewer parts; anchors `#free`, `#flow-plus`, `#live`.
- Components: `src/components/plans/`. `plan-card.tsx` (card anatomy: name + cost, art window, finish with rarity sparkles, perks as abilities, flavor text, illustrator credit). The finish sits on the **frame**, never over the art. `holo-tilt.tsx` is the only client island: it tilts the card toward the pointer and hands it the light. `your-card.tsx`: your banner and avatar printed in your plan's finish, the "Day N" seal (`plan-seal.tsx`), price / since / how long, and the next plan up. Its "Try it in …" switch runs the next finish over your card like a laminator, in CSS only (`group-has-checked`). `card-action.tsx`: per-card action by viewer. `card-art.ts`: demo art, credited.
- Foil CSS lives in `globals.css` (`foil`, `foil-live`, `foil-text`, `holo-tilt`, `card-glare`): the theme's own colors under a light at `--foil-x/--foil-y` (registered properties). Pastel iridescence in Aqua, fire in Ember. Idle cards drift; `data-active` hands the light to the pointer. Variants retune `foil` through inputs (`--foil-mix`, `--foil-b`, `--foil-d`), never by redefining its variables (utility order isn't guaranteed).
- No checkout yet: paid actions are "Checkout opens soon" tickets and a disabled "Upgrade to …". Never a button that pretends to charge.
- Data: plans, prices and finishes in `src/lib/plans.ts` (client-safe). The viewer's plan and start date come from `getViewerPlan()` in `src/lib/plan-status.ts` (server-only, uncached, deduped per request).

Reads in `src/lib/favorites/queries.ts` (`getViewerFavorites()`, per request, uncached); writes in `src/app/(site)/favorite-actions.ts`. Tests: `tests/e2e/favorites.spec.ts`.

## Gallery (`/[handle]/gallery`, characters, collections)

Concept: the artist's **creative center**, not a tab of loose images. Three kinds of thing: a **piece** (`artworks`) stands alone; a **character** (OC) has a page of their own with their art in sections; a **collection** groups pieces. One piece can be on several characters and collections. Visual language: the studio's files. Characters are **file folders** (name on the index tab, dyed in their colors, cover clipped on, sheets sticking out), collections are **stacks of prints**, and a character's page is their **reference sheet** on paper. Art is never cropped.

- Pages: `src/app/(site)/[handle]/gallery/page.tsx` (shelves: Characters, Collections, Every piece), `[handle]/characters/[slug]/page.tsx` (ref sheet: color bar, cover, facts box with designed by / kept by, swatches with hex, personality circled in pen, Save {name}, adoption footer linking to `/{handle}/adoptables#id`; story; sections Design → Outfits → Expressions & poses → Alternate versions → Art), `[handle]/collections/[slug]/page.tsx`. All static; they load Caveat for the asides.
- Components: `src/components/gallery/`: `character-folder.tsx`, `collection-stack.tsx`, `ref-sheet.tsx`, `piece-wall.tsx` (justified rows + `Lightbox` + heart; client), `character-actions.tsx` (save, copy link, swatches). Owner tools in `owner/`: `gallery-owner.tsx` (`OwnerButton`, `ShowFor`, `GalleryWall` with each piece's "…" menu, `GalleryDialogs`), dialogs for Add art (up to 12, `prepareImage` + AI check, upload to `art/<id>/gallery/`), piece, character (live ref card) and collection, opened from anywhere through `owner/store.ts`. Owner-ness is decided in the browser (`useViewerId()` from the favorites store vs. the profile's id), so pages stay static; the actions check again.
- Data: `src/lib/gallery/`: `types.ts` (sections, limits, slugs; client-safe), `assemble.ts` (rows → `Gallery`, `galleryIndex()` for the dialogs; tested), `server.ts` (Supabase reads), `queries.ts` (cached `getGallery(handle)`, tag `gallery:<handle>`), `demo.ts` (Kinako, Pip, Marsh, Mira's collections; drop with the demo data). Writes: `src/app/(site)/[handle]/gallery/actions.ts`, as the artist under RLS. Tables in `supabase/migrations/*_gallery.sql` (triggers: own art, covers and adoptables only; limits 2000 pieces / 100 characters / 100 collections / 300 per character).
- **Pictures from posts** (`*_post_pictures_in_gallery.sql`): every image post hangs its pictures in the gallery, one piece per picture (`artworks.post_id` + `post_image`), made by the `posts_hang_in_gallery` trigger, titled from the caption (`private.caption_title()` = `captionTitle()` in `types.ts`). ## Messages (direct messages, real-time)

Concept: **studio mail**, letters between studios. The card is a column on lg+, a toggle below.
- Light: the conversation takes the other person's art color (`--tint`, from their banner palette via `glowOf()`): `chat-light` washes the thread, `tint-bubble` shades their bubbles (pale in Aqua, deep in Ember; lightness from the theme, so contrast never depends on the art). Paper bits: `postage`, `cancel-lines`, `tint-ink`, `sketching` in `globals.css`. (`/requests` has its own commission-art stamp and postmark in `components/commissions/requests/postage.tsx`.)
- Entry points: "Message" on profiles (`message-button.tsx`; visitors get the sign-in link), the commission dialog's message button, the round `MessageIconButton` on `/requests` postcards, the header's Messages button (`messages-menu.tsx`: dropdown inbox on sm+, full-screen inbox on phones; hidden under 390px, where the account menu carries Messages and a dot), and any code via `openChat(handle)` / `openInbox()` from `store.ts`.
- **Connections (performance rule, sized for ~5k people online, most just browsing):** Realtime connections are capped per plan (Pro with the spend cap: 500), so **nobody holds a WebSocket unless their chat window is open** (or minimized). Everyone else gets a **pulse** over plain HTTP straight to Supabase, `rpc("message_pulse")` (unread count + newest arrival from others; RLS-scoped, ~1 ms even with 200 conversations, ~0.4 KB per answer; never touches Vercel). Rhythm (`store.ts`): 20s while you use the page, 60s when it's idle 2+ min, 90s in a background tab, 5 min after 15 min in the background, ±15% jitter; one tab per browser asks and shares the answer over a `BroadcastChannel`. Only when it changes does the inbox load (Server Action). Budget at 5k online ≈ 150 pulses/s. Opening the chat joins the private `inbox:<user id>` channel (instant messages, read receipts) plus the open conversation's `chat:<id>` (typing, presence: "Here now"); the socket closes 30s after the window does; if it drops while chatting, pulses run every 5s. The inbox list loads lazily (hovering the button, opening the chat); the badge comes from the pulse. Messages already waiting when a page opens show as a badge, not a letter. **Switch** `NEXT_PUBLIC_MESSAGES_LIVE=visible` to also keep a socket while a tab is visible (instant letters everywhere, ~1 connection per visible tab: needs the spend cap off, $10 per 1,000 connections; pulses then come only from background tabs). Keep it this way when adding live features: piggyback on the open-chat socket or the pulse, never a site-wide socket.
- **Arrivals** (`store.ts` `announceArrival`): a message whose conversation isn't on screen drops an airmail **letter** on the page (`incoming-letter.tsx`: Reply, dismiss, 8s, hovering holds it; at the top on phones), swings the header button, puts "(n)" in the tab title (`tab-badge.tsx`) and rings the **studio chime** (`src/lib/messages/chime.ts`: Web Audio, no files; a paper swish + a music-box tune in D major pentatonic, a different tune per sender, picked from their handle). One tab speaks per message (visible first, `claim()` via localStorage). Browsers allow sound only after a click on the page; the chime arms on the first one. Toggles in the inbox header (`alert-toggles.tsx`, kept in localStorage by `prefs.ts`): sound (on by default; turning it on plays your own tune) and desktop alerts while the tab is in the background (asks permission).
- Client store (`store.ts`): `<MessagesSession>` in the header says who's signed in. Live events reach the open conversation through `onLive()`; `resync` means reload (socket back, or a pulse brought news). Unread = newest message isn't yours and is newer than your `last_read_at`.
- Server: `src/app/(site)/message-actions.ts` (`loadInbox`, `openThread`, `loadEarlier`, `startConversation`, `sendMessage`, `markRead`, `setArchived`) over `src/lib/messages/server.ts`, all as the signed-in user (RLS). Client-safe types and limits: `src/lib/messages/types.ts`; local-clock times: `time.ts`; picture upload/signing: `upload.ts`.
- Data (`supabase/migrations/*_direct_messages*.sql`): `conversations` (one per pair: `user_a` < `user_b`, or an account + `demo_handle`; inbox preview columns kept by a trigger; made on the first message, never on open), `conversation_members` (each side's `last_read_at`, `archived_at`; a new message un-archives), `messages` (body ≤ 2000, `images` ≤ 4 in the **private** `messages` bucket at `<conversation id>/<sender id>/…`, read through signed URLs). Triggers broadcast with `realtime.send` and brake spam (40 new conversations a day, 20 messages a minute). `realtime.messages` policies: your own inbox topic (broadcast only), and broadcast + presence on the chat topics of conversations you're in. `message_pulse()` (security invoker) is the only function the browser calls.
- Demo artists have no account: messages to them are stored (`demo_handle`) and the thread says nobody will write back. Drop the column with the demo data.
- Not yet: report/block in chat (comes with the reporting brief), message notifications by email, commission orders inside the conversation. Tests: `tests/e2e/messages.spec.ts` (no socket while browsing, two browsers live, letter + chime + title, "Here now", archive, privacy, demo).

## Images: originals, thumbs, delivery, backup

Rule (approved 2026-10-12, roadmap brief "original images, cheap and safe"): **keep the original, serve copies.** Storing every file is cheap; sending big files to everyone who scrolls is what costs.

- Three files per picture, all made in the browser by `prepareImage(file, max, { thumb, original })`: the **display** copy (`art/<uid>/<folder>/<uuid>.<ext>`, ≤ 2400px), a **thumb** beside it (`<uuid>.thumb.<ext>`, ≤ 1024px; profile pictures 192px) and the **original** in the private `originals` bucket at the same path (the file itself, metadata stripped without re-encoding by `src/lib/images/formats.ts`: GPS, camera, names, XMP, C2PA go; color profile, transparency, animation, JPEG orientation stay). GIFs: the display copy is the stripped file; their thumb is a still, which the loader never swaps in (`toImageAsset` passes it as `ImageAsset.still`, for walls that play GIFs only on screen). Art (posts, gallery, listings, deliveries) keeps originals; avatar and cover get thumbs only; About-board images neither.
- Rows store `{ path, width, height, palette, thumb?: {width,height,type}, original?: {width,height,type,bytes} }` (`StoredImage`, `src/lib/art-storage.ts`); thumb and original paths are derived (`variants.ts`). Schemas spread `variantFields` (`images/schema.ts`).
- **Serving:** `next/image` uses our loader (`images.loaderFile` → `src/lib/images/loader.ts`), never Vercel's optimizer: art comes straight from Supabase's CDN, the thumb for widths up to its own, else the display copy. `toImageAsset()` marks a src with its thumb as a fragment (`…webp#thumb=1024.webp`); the loader adds `#w=`. Browsers never send fragments, so URLs still work raw: strip `#…` before turning a src back into a path (`artPathOf`). Demo art gets `.thumb.webp` files from `npm run demo:art`.
- **Server check:** every Server Action that saves uploads calls `verifyUploads(images, { userId, folder, known })` (`images/verify.ts`, server-only): own folder, bytes match the extension (never SVG/HTML dressed as PNG), declared size, caps (originals ≤ 16384px a side / 100 MP / 25 MB; GIFs ≤ 2000 frames / 400 MP across frames), ranged reads. A refused upload's files are removed; missing thumbs/originals are dropped; `known` (the row before an edit) keeps what was stored. Delete with `removeFiles(images)` (all three files).
- **Originals out:** `originalUrl(image, { download })` (`images/originals.ts`) signs a 1h link; the bucket's RLS only lets the owner read, so check the viewer first (the buyer of a delivery).
- **Limits** (`*_originals_and_upload_limits.sql`): a restrictive insert policy on `art` + `originals`: 600 files a day, 5 GB stored (50 GB Flow+), via `public.under_upload_limits()`. `uploadArt()` turns the refusal into a readable message.
- **Backup** (Supabase's backups skip Storage files): hourly Vercel Cron `/api/cron/backup-art` copies new files of `art` and `originals` to an S3-compatible bucket at another company (Cloudflare R2), keyed `<bucket>/<path>`, cursor in `_state/`; daily `?sweep=1` deletes files gone from Supabase for 30 days. Logic in `src/lib/backup/` (RPCs `backup_objects_after` / `backup_objects_existing`, secret key only). Off until `BACKUP_S3_ENDPOINT`, `BACKUP_S3_BUCKET`, `BACKUP_S3_ACCESS_KEY_ID`, `BACKUP_S3_SECRET_ACCESS_KEY` (+ `BACKUP_S3_REGION`, `auto` for R2) are set; `CRON_SECRET` is set in production. The bucket's 30-day lock rules must cover only the `art/` and `originals/` prefixes (`_state/` is rewritten every run).
- Team: `npm run images -- thumbs [--apply] [--local]` backfills thumbs for older uploads (done in production 2026-10-14); `npm run images -- backup [--sweep]` runs the backup by hand. Tests: `src/lib/images/*.test.ts`, `tests/e2e/originals.spec.ts`.

## Made by humans: the AI check on uploads

- Rule (decided 2026-10-11): no generative AI anywhere in a posted image. Reporting, review and strikes are planned in `docs/roadmap.md` (brief "reporting, and keeping Artiflow human-made").
- Detector: `src/lib/ai-check/` is a standalone module, so reuse it for any new place that takes images. `signature.ts` is pure TS (browser, scripts, server): C2PA / IPTC / XMP, settings in PNG text and EXIF (A1111/Forge, ComfyUI, NovelAI, InvokeAI, Fooocus, Midjourney), and stealth settings in the alpha LSB. `browser.ts` has `assertMadeByHumans(file, bitmap?)`, which throws `AiImageError`.
- `prepareImage()` runs it before re-encoding, so every upload through it is covered. Callers catch `AiImageError` and render `<AiImageDialog>` (`src/components/uploads/`), which explains the refusal and files "I made this myself" requests (`ai_review_requests`, 10/day, no file kept, Server Action `requestAiReview`).
- Team: `npm run ai-check -- <files|folders>` checks files with the same detector; `npm run ai-check -- requests` lists open review requests (production, via `.env.local`).
- Tests: `npm run test:unit` (Node's test runner, `src/**/*.test.ts`) and `tests/e2e/ai-check.spec.ts`. When adding a generator, check it against a real file with `npm run ai-check` first, and add its layout to `signature.test.ts`.
- A clean result proves nothing (screenshots strip metadata). Never treat it as "verified human".

## Running locally: two modes

- `npm run dev:local` → http://localhost:3001 against the **local** Supabase (Docker). Starts Docker (macOS) and the stack if needed, applies new migrations, builds into `.next-local/`. Studio `127.0.0.1:44323`, emails in Mailpit `127.0.0.1:44324`. Throwaway data.
- `npm run dev:production` → http://localhost:3000 against the **production** Supabase from `.env.local` (Vercel uses the same project for Production/Preview/Development). Refuses to start if `.env.local` points at a local stack; prints a red "real data" banner.
- Both can run at once (separate ports and dist folders). Logic in `scripts/dev.ts` + `scripts/lib/local-supabase.ts` (shared with the e2e suite).
- The local stack is shared by every session on this machine: don't `supabase stop/start/db reset` while another session is using it.

## Tests (end-to-end)

- Playwright (`@playwright/test`, pinned) in `tests/e2e/`. Run `npm run test:e2e` (or `test:e2e:ui`).
- Needs Docker and the **local** Supabase stack: `npx supabase start` (API `127.0.0.1:44321`, Mailpit `:44324`, Studio `:44323` — ports moved off 543xx/556xx, which other local projects / macOS hold). The suite refuses to run against a non-local Supabase.
- Playwright builds the app into `.next-e2e/` (`NEXT_DIST_DIR`) and serves it on `localhost:3100` with the local stack's keys, so it never collides with `next dev` or `.env.local`.
- Local auth mirrors production: email confirmation is **on**. Tests read the real confirmation email from Mailpit (`tests/e2e/support/mailpit.ts`).
- Each test creates its own throwaway account (`e2e_<random>`) and deletes it afterwards. Wait for React hydration before typing into the controlled auth forms (see `open()` in `auth.spec.ts`).
- First suite: `auth.spec.ts` — sign up with email + password → blocked until confirmed → confirm via the email link → signed in on the new page → sign out → wrong password refused → sign in by email and by handle.
